## Day 1 — 研究構造そのものを研究する

**黒田教授**：最近、ずいぶん実装が増えたね。でも、そもそも何を研究しているの？

**佐伯副手**：だから構造を先に切っています。RQ、EXT、EXP、RXです。Issueにして、READMEにして、実験はその後。

**神谷D1**：ただ、構造化しただけで研究になったと思うのは危険です。RQ-003のVisualizationも、綺麗な図を出しただけならEvidenceではありません。

**中野B4**：でも、再現できたら何が嬉しいんですか？ 同じ絵がもう一回出るだけですよね。

**神谷D1**：つまり「再現できるArtifact」と「Evidence」を分ける必要があります。

**佐伯副手**：じゃあAcceptanceに入れます。VisualizationはArtifact。観測手順とProvenanceがあって初めてEvidence候補。

**三浦M2**：了解。実験側では最初からmanifestを出します。

**中野B4**：じゃあ、絵を作ることより「何を見たか」のほうが大事なんですね。

## Day 2 — 建築CorpusとIdentity

**三浦M2**：Architecture Corpusの試作を考えています。図面、写真、CAD、BIM、meshを同じWorkに紐付ける。

**佐伯副手**：`Work → Representation → Object → Geometry / Semantic / Provenance`ですね。

**神谷D1**：でもRepresentationが違うものを本当に同じObjectと呼べるんですか？ 写真の壁とCADの壁は同じものなのか。

**中野B4**：そもそも「同じ」って誰が決めるんですか？

**黒田教授**：それだ。RQ-006のIdentityは、データベースのID付けの話ではないかもしれない。

**三浦M2**：Geometryだけでmatchingすると、改修前後や別表現で壊れそうです。

**神谷D1**：Semanticだけでも駄目です。名前が同じでも別物はある。

**佐伯副手**：じゃあIdentityを `geometry + topology + semantic + provenance` の関係として定義する方向ですね。

**黒田教授**：ただし「同一」と「対応する」は分けよう。

**中野B4**：同じじゃなくて、似ているとか、対応しているとか？

**神谷D1**：そう。Identity、Correspondence、Similarityを混ぜない。

**佐伯副手**：新しいAcceptance候補にします。

## Day 3 — BATTAと建築生成

**三浦M2**：BATTAの最小構成を `Input → Parameter → Rule → Geometry → Output` にします。wall、divide、opening、repeatあたりから。

**黒田教授**：Grasshopperを作るの？

**三浦M2**：クローンではなく、建築研究用のパラメトリックルール系です。

**神谷D1**：重要なのはUIではなくRuleです。何が建築的知識として抽出されるのか。

**中野B4**：じゃあゲームにしたらダメなんですか？

**三浦M2**：むしろゲーム化するとRuleを操作できます。

**佐伯副手**：MADORIからRuleを抽出してBATTAへ渡す流れなら、既存作品をコピーせず構造だけ移植できます。

**黒田教授**：換骨奪胎だね。作品を持ってくるのではなく、関係を持ってくる。

**神谷D1**：ただし「抽出したRuleが本当に元作品の本質か」は検証が必要です。

**中野B4**：じゃあ、ゲームで遊んだ結果からRuleが変わったら？

**黒田教授**：それは面白い。Ruleは最初から固定された真理ではなく、操作によって発見される可能性がある。

## Day 4 — MaterialからArchitectureへ

**三浦M2**：土を材料にして、粒径、水分、混合、押出、積層、乾燥、収縮、ひび割れを経て壁を作るモデルを考えています。

**神谷D1**：GeometryからMaterialを推定するだけではなく、MaterialからProcess、Geometryへ逆向きに行くわけですね。

**黒田教授**：建築を完成形から見るのをやめる。

**中野B4**：家って、最初から家じゃないですよね。

**佐伯副手**：`Material → Process → Geometry → Building` をEXTとして整理できます。

**三浦M2**：小さい壁、アーチ、開口くらいから実験できます。

**神谷D1**：そして失敗を捨てない。ひび割れや崩壊も結果です。

**黒田教授**：むしろ失敗がMaterialとGeometryの関係を教えるかもしれない。

**中野B4**：じゃあ「建築を作る」じゃなくて「材料が建築になる過程を見る」？

**黒田教授**：その言い方のほうが研究になる。

## Day 5 — 時間・身体・光

**三浦M2**：EXP-002で静止画と時間変化を比較しています。plan、section、elevation、static 3D、animationを評価します。

**神谷D1**：Animationだから新しいとは言えません。静止画を順番に見れば同じなら、Animationの意味はない。

**三浦M2**：だから `temporal_relation` や `body_path`、`viewpoint_dependency` を評価項目にしています。

**中野B4**：でも人間って、そもそも建築を動画として見てませんか？ 歩いて、振り返って、光が変わって。

**黒田教授**：そう。建築を「物体」として固定すること自体が特殊な表現なのかもしれない。

**佐伯副手**：RQ-009のExperienceに接続できます。

**神谷D1**：ただし身体経験という言葉を便利に使わない。何が観測されたかを書かないといけない。

**三浦M2**：observer、frame_time、relation_noticed、interpretation、confidence、counterexampleを残します。

**中野B4**：じゃあ「建築の形」じゃなくて「建築との関係」を記録する？

**黒田教授**：また一段深くなった。

## Day 6 — Interactive ViewとSemantic Graph

**三浦M2**：PlotlyでSpace + Time + Semanticを一つのInteractive Viewにできます。objectをクリックしてGeometry、Semantic、Feature、Time、Camera、Provenanceを追えるようにする。

**佐伯副手**：JSONからRDF、BigQuery、BQMLまで繋げる構想とも合います。

**神谷D1**：でもInteractiveは情報を増やしただけになりがちです。

**中野B4**：クリックしたらいっぱい情報が出るのって、本当に発見なんですか？

**黒田教授**：重要な質問だね。Information量とDiscoveryを分ける。

**三浦M2**：評価にdiscoverabilityを入れます。StaticやPyVistaでは見つけにくかった関係が発見できるか。

**神谷D1**：さらにtraceability。発見した関係が元Geometryまで辿れる必要があります。

**佐伯副手**：Browser portabilityやperformanceもAcceptanceに入れます。

**中野B4**：じゃあUIそのものが研究じゃなくて、UIによって「何が見つかるか」が研究？

**黒田教授**：その通り。

## 一週間で発生したRQ候補

4. Static / Animation / Interactive ViewのRepresentation変換によって、建築について新たに発見可能になる関係は何か。
5. Geometry・Semantic・Time・Observation・Provenanceを統合したResearch Corpusは、建築研究における「対象」の定義を変えるか。
