## 建築研究をどう動かすか

**黒田（教授）**：建築のアニメーションを作ること自体が研究ではないよね。何を発見したいの？

**三浦（M2）**：じゃあまず作ります。静止画とアニメーションを同じGeometryから出して、比較できるようにします。

**神谷（D1）**：でも、それ静止画でも分かるなら、アニメーションにする意味がないですよね。

**中野（B4）**：そもそも「分かる」って誰が決めるんですか？

**佐伯（副手）**：そこを記録できるようにしましょう。観察者、視点、時間、気づいた関係、解釈、反証を残せばいい。

**黒田**：そう。Visualizationは結果じゃなくて、観測装置かもしれない。

**神谷**：ならEvidenceになる条件を決めないといけません。画像が綺麗だからEvidence、では駄目です。

**三浦**：じゃあmanifestにrenderer、camera、fps、seed、Geometryの情報も入れます。

**佐伯**：それで再現できるなら、研究構造としては `RQ → EXT → EXP → RX → Evidence` に乗せられます。

**中野**：Evidenceって、あとから見た人も同じことに気づく必要がありますか？

**神谷**：必ずしも同じ解釈ではない。ただし、何を観察したのか追跡できる必要がある。

**黒田**：いいね。そこから「建築の経験は客観的なGeometryだけでは記述できない」という問いまで行ける。

## Geometryと意味

**中野**：GeometryとSemanticを分けるの、なんでですか？

**黒田**：いい質問。分けないと何が形で何が意味なのか分からなくなるから。

**神谷**：ただし完全分離すると、今度は「この壁」という対象を追跡できなくなる。

**三浦**：じゃあObjectを中間に置きます。Geometry、Topology、Semantic、ProvenanceをObjectに紐づける。

**佐伯**：Work → Representation → Object → Geometry / Topology / Semantic / Provenance、そこからFeature。

**黒田**：それならCAD、BIM、Mesh、図面、写真まで同じ研究Corpusに入れられる。

**中野**：写真とMeshが同じObjectになるの、ちょっと面白いですね。

**神谷**：ただしIdentityの定義が必要です。見た目が似ているから同じ、では研究として弱い。

## BATTAと生成

**三浦**：BATTAも `Input → Parameter → Rule → Geometry → Output` にすれば、研究側のGeometry graphとつながります。

**中野**：それってゲームにしたらダメなんですか？

**黒田**：むしろゲームにしてみよう。ルールを操作すると建築が変わるなら、建築生成の規則を経験できる。

**神谷**：ただのゲームになったら研究から外れます。何を評価するか必要です。

**佐伯**：Rule、Constraint、Generation、EvaluationをJSONにして、あとでSemantic Graphにもできる。

**三浦**：さらにBigQueryに入れて、BQMLで次の候補を予測する。

**中野**：予測した建築って、まだ存在してないですよね？

**神谷**：そう。予測はFactではない。ここは研究ルールとして明記しましょう。

**黒田**：その区別は重要だね。生成したものと観測したものを混ぜない。

## Materialへ

**中野**：じゃあ土から建築を作る場合は？

**三浦**：`Material → Process → Geometry → Building` にできます。水分、粒径、押出、積層、乾燥、収縮までパラメータ化する。

**神谷**：MaterialからGeometryへの変換だけでなく、ひび割れや失敗もRXとして残せます。

**佐伯**：つまりFailureもEvidenceになり得る。

**黒田**：失敗を消すな。境界条件が分かれば、それは研究結果だ。
